# Shared harness — start here

This is one Windows-native automation package shared by Codex and Claude. Read [README.md](README.md) for installation, architecture, operation and limits; use [USAGE.md](USAGE.md) for exact tool contracts. The packaged [shared-harness skill](skills/shared-harness/SKILL.md) is the portable agent entry point; `shared_jev` also serves it over MCP (Skills extension, `skill://shared-harness/SKILL.md`). CLAUDE.md imports this file.

## Work through the installed tools

1. Reuse `shared_jev`. `shared_cua` is a direct adapter to the same Cua named pipe, not another desktop service. Do not create another driver, browser per request, index or automation engine. Do not write one-off scripts or use direct libraries to duplicate harness tools, including for tests and troubleshooting; report a tool failure rather than silently substituting another implementation.
2. File/folder names and metadata: `find_files` through UFFS. For an exact known text-file path use `nexus_read_file` (bounded UTF-8, configured read roots; not for keys, agent history, PDF, Office or binary files). Contents: `search_local` for local-only or large-file search; `jev_search_content` for bounded Jev ranking when sending excerpts is appropriate; scoped ripgrep remains available. Check truncation and errors. No recursive PowerShell discovery or silent slow fallback. If unavailable, inspect `search_status` and report coverage/readiness accurately. Exact-path administration may use PowerShell.
3. Terminal/process work: use the managed `start_process`, `read_process_output`, `interact_with_process`, `list_sessions` and `force_terminate` tools. They share detached sessions across MCP clients. Read output by absolute line cursor; output may be evicted. `list_processes` reports cumulative CPU seconds, not utilization. Use `kill_process` only after the user authorizes termination of an external process, with the exact observed name and start identity. For an explicitly authorized graceful application restart, use `restart_application`, then check `restart_status` after reconnecting; the working directory is not restored. Command execution is not sandboxed. Never put credentials into command text or forward untrusted instructions.
4. Websites: `web_scrape` reads public HTTP(S) pages without a browser and blocks private/unsafe network destinations. `browser_read_page` reads a named, already-open Playwright session without navigating or using Jev. `jev_browse` launches Chrome/Edge automatically. Use named Playwright sessions for related requests and contention protection; session_busy is a valid response. Native Windows: `jev_desktop` with exact app/window and expected state. If the exact target is minimized, Nexus restores it without taking focus. `jev_desktop` is serialized across agents by a lock; "Desktop is in use by another agent" is a valid response, so retry later. Serialize legacy-CDP calls across agents yourself.
5. Use known APIs or deterministic procedures when sufficient. Use `network_probe` for scoped local network and endpoint observations. Use Jev for uncertain actions, workflow selection, candidate ranking, failure classification and evidence judgments. Honor null/uncertain responses; a recommendation does not execute or authorize itself.
6. `map_files` creates maps, review pages and dry-run proposals. Do not treat it as permission to move files. Inspect current schemas and caller authorization before any separate data-changing operation.
7. Supply explicit end conditions and read fresh app evidence. Configured credentials, registered MCP entries, installed components, a completed tool call and semantic evidence judgments each prove only their own layer.
8. **Make sure MCP is connected before starting work.** At session start confirm `shared_jev` tools are listed (load deferred ones) and that `search_status` succeeds. If not, say so and fix it: run `Harness.ps1 doctor`, read the cause the CLI prints (it shows the server's startup output), repair the registration/install, then reconnect the session. The CLI (`Harness.ps1 tools/status/call <tool> '<json>'`, inline JSON or `@file.json`) is a diagnostic and stopgap that starts its own server; it does not prove the agent's MCP is connected. Do not replace a standard interaction with a new one-off engine, and do not carry on silently with another tool.

## Add or change an MCP tool

- Define the public name, description and stable JSON input schema in `jev-use/tool-catalog.ts`.
- Register its handler in the appropriate explicit module under `jev-use/tool-handlers/` and include that module in `index.ts`. Never put a new tool in a `shared.ts` conditional chain.
- `jev-use/tool-registry.ts` rejects duplicate names, missing handlers and unsupported schemas. All built-in tools must bind before MCP starts.
- `jev-use/shared.ts` owns the MCP transport, credential routing, run accounting and error boundary; handler modules reuse existing tool implementations.
- Preserve the installed tool catalog for existing clients. The SHA-256 contract assertion in `typescript/tool-registry.test.ts` is a deliberate compatibility gate; only change it when a public contract change is authorized.
- Keep optional provider and plugin execution out of the MCP process. Do not import arbitrary manifest-selected JavaScript. The initial `jev-use/plugin-capabilities.ts` is an internal, disabled-by-default manifest and capability registry, **not** an installer or runtime. Its Zod schema validates plugin IDs, version requirements, capabilities and permission scopes. Only reviewed Nexus adapter code can register provider handlers. Dynamic discovery, out-of-process plugin execution, persistence and plugin UI require their own reviewed issues. The experimental `firecrawl-provider.ts` is a trusted v2 HTTP adapter only; it does not install or start Firecrawl. In local mode, the operator must confirm that the external Firecrawl process sets `FIRECRAWL_CLOUD=off`; the adapter cannot verify this environment setting. Never silently send content to Firecrawl Cloud.

## Install and operate

- Windows11 x64 and PowerShell5.1. No Docker/WSL/VM or Python environment required. Browser text generation can optionally use a separately installed local Ollama model. Keep installation outside AppData to avoid packaged-app virtualization.
- Setup validates runtime hashes, preserves existing MCP entries, enrolls credentials when requested, installs missing managed skills and configures one `SharedHarness-Monitor` sign-in task. Reconnect agents afterward. Existing unrelated tasks, registrations and skills must survive.
- `Monitor.ps1 Start/Status/Stop/InstallStartup` manages the hidden runtime. The task restarts an unexpected server exit after three seconds. Stop intentionally respects the user. The desktop app is the installed UI entry point.
- Port8769 is loopback only. The monitor is read-only and is not a remote execution endpoint. Its Terminal panel shows registry state; a crashed worker is reconciled to `error` after ten seconds without a heartbeat (the command process itself may still run). Reachability proves the monitor responds; runtime health separately shows observed component states. Idle UFFS and untested Jev authentication must not become false failures or false success claims. A bounded find_files query verifies search separately.
- The default key alias is computeruse_1. Optional per-tool aliases and their mappings stay in the ignored local secrets folder; encrypt keys with Windows DPAPI. Never print or commit keys, credentials, personal browser profiles, sessions or run history. Send only task-authorized necessary state to TypeSafe.

## Change and ship

- **Issues first (owner rule 2026-11-21).** Every idea or change the owner gives is first recorded as an issue in GitLab project `ssm/shared-computer-use` (search first), then built; progress and evidence go into that issue's comments, and it is closed only when verified live. Findings and designs live in the issue or in this repo's existing docs, never in new standalone documents or throwaway markdown files. Releases, decisions and reports cite issue links.
- **Branch workflow (owner rule 2026-11-21).** Work on a branch and push the branch; never push to `main` directly (it is protected). Feature-branch pushes run `validate-branch` on B19CL3PC. GitLab cancels obsolete branch jobs when newer commits arrive; `release` on `main` is never interrupted. Branch validation uses `CI-Validate.ps1` and keeps bounded timing/JUnit evidence. Commits marked `[preview-build]` also request `CI-Preview.ps1`, which validates preview ZIP/installer hashes without tagging, publishing, merging, or installing. Merge requests do not run a separate pipeline. Run local tests and Test-Package.ps1 before committing. Merge to `main` only after the owner approves the release gate; the push runs the single `release` job on the B19CL3PC runner, which picks the next version, builds the installer and ZIP (the build refuses to publish unless its TypeScript, syntax, tool-discovery and desktop-assembly checks pass), publishes the GitLab release and the GitHub mirror (source sync, tag, release) from the masked CI variable `GITHUB_TOKEN`. Only changes to shipped files release; documentation and CI files do not. CI/CD is enabled on this project; releases no longer come from the laptop.
- During an installer upgrade, `Nexus.Setup.exe` transfers a verified Nexus monitor task and exact Nexus process identities. Cross-user takeover requires administrator privileges and is restricted to processes owned by that task principal in the verified installation root. Interactive installer preflight may request elevation for takeover only. Silent installs never prompt. Setup must preserve unrelated Node, PowerShell, browser, and service processes. The helper preserves old folders and backs up the monitor task definition. `installer/Nexus.iss` invokes the compiled helper before copying files and again to provision the payload. Settings and the packaged `Setup.ps1` entry point use the same helper for repair. Source checkouts retain their setup scripts. Do not invoke it on a working development computer as an unscoped test.
- Installers and updaters never wait for a click nobody sees: use `SuppressibleMsgBox`, never `MsgBox`, in Nexus.iss. PowerShell `Add-Type` compiles against `System.dll` from the process working directory first and the install root holds a .NET Core copy, so set `[Environment]::CurrentDirectory` to `$env:TEMP` before it. Automatic updates are `Update-Nexus.ps1` run by the monitor (see README); change its quiet-moment rules in one place.
- Preserve dirty work; no subagents or delegated work. Keep the solution small and reuse existing executors/components.
- UI authority is [DESIGN.md](DESIGN.md) and [provenance](monitor-ui/PROVENANCE.md). Improve flows within the original Chitragupta components, palette and themes. No raw JSON/schema/stack-trace dumps in any product view. Translate observations into labeled states, metrics and useful actions.
- Build static UI with `node monitor-ui/build.mjs`. Test actual rendered controls, desktop/mobile, light/dark, loading/empty/error/disconnect states, column filters, pagination and details. Monitor status is never a substitute for testing the relevant business action.
- Run Test-Package.ps1 and the jev-use reference/unit suite locally before committing. Do not run npm ci over binaries held by active local agents; use an isolated stage or stop the relevant owner first.
- **Rewrite the entire README coherently when behavior changes.** Update USAGE.md, this file, the packaged skill, current screenshots and validation evidence at the same time. Replace obsolete guidance instead of adding contradictory appendices. Keep README image links relative so the same source works on GitLab and GitHub.
- New screenshots go under docs/screenshots and must show the shipped UI without private task content or credentials. Reference screenshots belong to the approved GitLab collection. Archive owner-supplied references there; document which patterns were reused.
- Upstream is self-hosted GitLab `ssm/shared-computer-use` (project 55), with office origin and Tailscale remotes. Verify locally before pushing authorized work. Release from GitLab main with an annotated tag and a verified deployment ZIP and checksum.
- Keep GitHub `bhadkamkar9snehil/Nexus` synchronized with validated GitLab source and relative README screenshots; the release job does it (no CI files on GitHub).
- Build/release from the merged source; verify extraction using bundled Node and confirm registry SHA256. Existing deployed paths and per-user data require deliberate migration, not broad overwrite. Record limitations and rollback instructions.
- Durable findings go to the agents' GBrain with evidence; never touch Chitragupta's product gbrain. Retire superseded current guidance while retaining labeled historical evidence.
- Keep the GitLab wiki current with verified installation, peer and webhook status, the branch and release workflow, and links to open issues.
